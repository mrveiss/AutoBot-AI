# Single-Host AutoBot Deployment

**Issue #2961** | Last updated: 2026-04-12

This document covers the complete lifecycle for deploying AutoBot on a single machine using
`install.sh` — from first boot through wizard configuration, post-deployment verification, and
maintenance. It complements [`docs/runbooks/SINGLE_HOST_DEPLOYMENT.md`](../runbooks/SINGLE_HOST_DEPLOYMENT.md),
which covers the low-level Ansible provisioning path.

---

## What `install.sh` Does (and Does Not Do)

`install.sh` is a self-contained bootstrap script that turns a blank Debian/Ubuntu host into a
fully operational SLM Manager node. After it finishes, you use the **SLM Web UI Setup Wizard** to
add and configure fleet nodes (which may all be the same machine).

### install.sh Phases

| Phase | What Happens |
|-------|-------------|
| 1 — Pre-flight | Checks root, systemd, Debian/Ubuntu, disk space (5 GB), memory (2 GB), internet |
| 2 — System Setup | Installs Python 3.14, Node 20, Ansible, nginx, git, openssl, rsync; creates `autobot` user with passwordless sudo; generates ED25519 SSH key at `/home/autobot/.ssh/autobot_key`; copies to `/etc/autobot/ssh/` |
| 3 — Code Deployment | Clones `Dev_new_gui` to `/opt/autobot/code_source`; rsyncs `autobot-slm-backend`, `autobot-slm-frontend`, `autobot-slm-agent`, `autobot_shared`, `autobot-infrastructure` to `/opt/autobot/` |
| 4 — Ansible Deployment | Generates `inventory/localhost.yml`; writes `/etc/autobot/slm-secrets.env` (secret key, encryption key, admin password, server IP, network subnet/gateway); runs `deploy-slm-manager.yml --skip-tags seed,provision` |
| 5 — Service Verification | Waits up to 7 minutes for `autobot-slm-backend` to pass `GET /api/health`; verifies PostgreSQL and nginx |
| 6 — Register Local Node | Authenticates with SLM API; registers the machine as node `00-SLM-Manager` with roles `slm-backend`, `slm-frontend`, `slm-database`, `slm-monitoring`; assigns code source |
| 7 — Finalize | Writes install marker at `/opt/autobot/.autobot-installed`; saves credentials to `/root/autobot-credentials.txt` |

### What install.sh Does NOT Deploy

`install.sh` only deploys the **SLM Manager** (the control plane). The following are provisioned
later through the SLM Wizard:

- `autobot-backend` (AI agent engine, FastAPI)
- `autobot-frontend` (user chat UI, Vue 3 + nginx)
- `autobot-browser-worker` (Playwright automation)
- `autobot-npu-worker` (hardware AI acceleration)
- Ollama / vLLM / AI stack services

For a true single-host deployment, the Wizard assigns all roles to the same machine after
`install.sh` completes.

## Prerequisites

### Hardware

| Aspect | Minimum | Recommended |
|--------|---------|-------------|
| CPU cores | 4 | 8+ |
| RAM | 8 GB (SLM only) / 16 GB (full stack) | 32 GB+ with GPU |
| Storage | 20 GB (SLM only) / 100 GB (full stack with models) | 200 GB+ NVMe SSD |
| GPU | Optional | NVIDIA GPU for hardware-accelerated inference |

### OS Requirements

- **Debian 11/12** or **Ubuntu 22.04/24.04 LTS** (64-bit)
- **systemd** running as PID 1 (required — WSL2 needs `[boot] systemd=true` in `/etc/wsl.conf`)
- Root or sudo access
- Outbound internet access (to reach `github.com`, `deb.nodesource.com`, PyPI)

### WSL2-Specific Setup

```bash
# /etc/wsl.conf — add if missing, then restart WSL: wsl --shutdown
[boot]
systemd=true
```

After adding, restart WSL (`wsl --shutdown` from Windows, then reopen WSL). Verify with:

```bash
ps -p 1 -o comm=   # Must output: systemd
```

## Step 1: Run install.sh

```bash
# Option A: Direct from GitHub (blank server)
curl -fsSL https://raw.githubusercontent.com/mrveiss/AutoBot-AI/Dev_new_gui/install.sh | sudo bash

# Option B: After cloning
git clone https://github.com/mrveiss/AutoBot-AI.git
cd AutoBot-AI
sudo ./install.sh

# Unattended (no prompts, auto-generated admin password)
sudo ./install.sh --unattended

# Custom admin password + specific branch
sudo ./install.sh --admin-pass=MySecurePass --branch=Dev_new_gui

# Multi-interface host: specify which IP to bind
sudo ./install.sh --ip=192.168.1.100
```

When the script finishes, credentials are printed to the terminal and saved to
`/root/autobot-credentials.txt`:

```
SLM URL:   https://<server-ip>/slm/
Username:  admin
Password:  <auto-generated>
```

The self-signed TLS certificate will trigger a browser warning — click through or add the cert to
your trust store.

## Step 2: SLM Setup Wizard

Open `https://<server-ip>/slm/` and log in with the admin credentials.

The first login triggers the **Setup Wizard**. For a single-host deployment, all steps assign
roles to the same machine.

### Wizard Step 1 — Add Fleet Node

Click **Fleet > Add Node** and enter:

| Field | Single-Host Value |
|-------|------------------|
| Hostname | `<server-ip>` or hostname |
| SSH User | `autobot` |
| SSH Port | `22` |
| Auth Method | Key (uses `/etc/autobot/ssh/autobot_key`) |
| Import Existing | Yes (node is already running) |

The node is tested via SSH. If the test fails, verify:
- `autobot` user exists with passwordless sudo
- SSH key is at `/etc/autobot/ssh/autobot_key` (private) and `autobot_key.pub`
- SSH server is running: `systemctl status ssh`

### Wizard Step 2 — Assign Roles

For a single-host deployment, assign all roles to the same node:

| Role | Purpose |
|------|---------|
| `slm-backend` | SLM control-plane API |
| `slm-frontend` | SLM admin dashboard |
| `slm-database` | PostgreSQL (SLM user management) |
| `slm-monitoring` | Prometheus + Grafana |
| `backend` | AutoBot AI agent engine |
| `frontend` | AutoBot user chat UI |
| `database` | Redis (cache + sessions) |
| `aiml` | Ollama inference stack |
| `browser` | Playwright browser automation |

### Wizard Step 3 — Provisioning

Click **Provision** (or run `ansible-playbook provision-fleet-roles.yml` directly).

This runs in 6 sub-phases:
1. System dependencies
2. Service unit creation
3. Code sync from SLM code source
4. Secrets generation (TLS certs, Redis auth, API tokens)
5. Configuration rendering (Ansible templates → live `.env` files)
6. Service enable + start

**Expected duration:** 5–15 minutes (longer on first run when pulling Ollama models).

## Environment Variables Reference

AutoBot uses two distinct env var namespaces. Mixing them causes startup failures.

### `AUTOBOT_*` — Backend Service Configuration

These are read by `autobot_shared/ssot_config.py` via `pydantic-settings`. All have sane
single-host defaults and are rendered to `/etc/autobot/backend.env` by Ansible.

**Network**

| Variable | Default (single-host) | Description |
|----------|-----------------------|-------------|
| `AUTOBOT_REDIS_HOST` | `127.0.0.1` | Redis server IP (use `127.0.0.7` for loopback alias) |
| `AUTOBOT_REDIS_PORT` | `6379` | Redis port |
| `AUTOBOT_REDIS_PASSWORD` | _(empty)_ | Redis password (blank = no auth) |
| `AUTOBOT_CHROMADB_HOST` | _(from ai-stack host)_ | ChromaDB host |
| `AUTOBOT_CHROMADB_PORT` | `8100` | ChromaDB port (NOT 8000 — conflicts with SLM) |
| `AUTOBOT_OLLAMA_HOST` | `127.0.0.1` | Ollama host |
| `AUTOBOT_OLLAMA_PORT` | `11434` | Ollama port |
| `AUTOBOT_BROWSER_SERVICE_HOST` | _(from fleet)_ | Browser worker host |
| `AUTOBOT_BROWSER_SERVICE_PORT` | `3000` | Browser worker port |
| `AUTOBOT_TTS_WORKER_HOST` | `127.0.0.1` | TTS worker host |
| `AUTOBOT_TTS_WORKER_PORT` | `8083` | TTS worker port (NOT 8082 — WSL2/Hyper-V reserved) |

**Important:** Do NOT use plain `REDIS_HOST`. The backend only reads `AUTOBOT_REDIS_HOST`.

**Deployment Mode**

| Variable | Values | Description |
|----------|--------|-------------|
| `AUTOBOT_DEPLOYMENT_MODE` | `local`, `hybrid`, `distributed`, `production` | Infrastructure topology |
| `AUTOBOT_USER_MODE` | `single_user`, `single_company`, `multi_company`, `provider` | User management model |

See [Deployment Modes](#deployment-modes) below for full details.

**LLM — 6-Tier Model Mapping**

| Variable | Default | Tier |
|----------|---------|------|
| `AUTOBOT_ROUTING_MODEL` | `llama3.2:1b` | Tier 1 — routing/orchestration |
| `AUTOBOT_CLASSIFICATION_MODEL` | `gemma2:2b` | Tier 2 — intent classification |
| `AUTOBOT_LIGHT_PROCESSING_MODEL` | `phi3:mini` | Tier 3 — extraction, formatting |
| `AUTOBOT_INSTRUCTION_MODEL` | `mistral:7b-instruct` | Tier 4 — RAG, entity extraction |
| `AUTOBOT_SYSTEM_MODEL` | `dolphin-llama3:8b` | Tier 5 — system commands, security |
| `AUTOBOT_DEFAULT_LLM_MODEL` | `qwen3.5:9b` | Tier 6 — user-facing chat, code, research |
| `AUTOBOT_LLM_PROVIDER` | `ollama` | LLM provider (`ollama` or `openai`) |
| `AUTOBOT_LLM_ENDPOINT` | `http://127.0.0.1:11434` | LLM API base URL |

**Security**

| Variable | Description |
|----------|-------------|
| `SECRET_KEY` | FastAPI session key (min 32 chars) |
| `AUTOBOT_JWT_SECRET` | JWT signing key (min 32 chars) |
| `AUTOBOT_INTERNAL_API_KEY` | Shared secret for SLM→backend proxy auth |
| `CORS_ORIGINS` | Allowed CORS origins (`*` for dev) |

**PostgreSQL (non-single_user modes only)**

| Variable | Default | Description |
|----------|---------|-------------|
| `AUTOBOT_POSTGRES_HOST` | `127.0.0.1` | PostgreSQL host |
| `AUTOBOT_POSTGRES_PORT` | `5432` | PostgreSQL port |
| `AUTOBOT_POSTGRES_DB` | `autobot_users` | Database name |
| `AUTOBOT_POSTGRES_USER` | `autobot_app` | Database user |
| `AUTOBOT_POSTGRES_PASSWORD` | _(generated)_ | Database password |

### `SLM_*` — SLM Manager Configuration

These are written to `/etc/autobot/slm-secrets.env` by `install.sh` and read by the SLM backend.

| Variable | Description |
|----------|-------------|
| `SLM_SECRET_KEY` | Flask/JWT secret key (64 hex chars) |
| `SLM_ENCRYPTION_KEY` | Data encryption key (64 hex chars) |
| `SLM_ADMIN_PASSWORD` | SLM admin UI password |
| `SLM_EXTERNAL_URL` | Public HTTPS URL (e.g., `https://192.168.1.100`) |
| `SLM_HOST` | Machine's primary IP (used by Ansible for service discovery) |
| `NETWORK_SUBNET` | Local subnet CIDR (e.g., `192.168.1.0/24`) |
| `NETWORK_GATEWAY` | Default gateway IP |

**Permission requirement:** `/etc/autobot/slm-secrets.env` must be `640 root:autobot`.
Looser permissions cause Ansible pipe lookups to fail silently.

## Deployment Modes

### Infrastructure Mode (`AUTOBOT_DEPLOYMENT_MODE`)

Controls how the backend discovers and addresses services.

| Mode | When to Use |
|------|-------------|
| `local` | All services on loopback (`127.0.0.x` aliases) |
| `hybrid` | Mix of local and remote services |
| `distributed` | Each service on a separate VM/host |
| `production` | Distributed with hardened TLS and auth enforcement |

For single-host deployments, use `local` (loopback aliases) or `distributed` (the default, which
also works when all IPs resolve to localhost).

### User Management Mode (`AUTOBOT_USER_MODE`)

Controls authentication and database requirements.

| Mode | Auth Required | PostgreSQL | When to Use |
|------|--------------|------------|-------------|
| `single_user` | No | No | Personal/dev installs, single developer |
| `single_company` | Yes (JWT) | Yes | Small team, one organization |
| `multi_company` | Yes (JWT + org) | Yes | Service provider, multiple organizations |
| `provider` | Yes (JWT + full RBAC) | Yes | Hosting AutoBot for external clients |

**Important for single_user mode:** Auth is disabled, so the login page in the frontend is
cosmetic — the backend accepts all requests without credentials. This is intentional. If you see a
login page appearing despite `single_user` mode, this is a frontend display issue only; API calls
will succeed without authentication.

## Post-Deployment Verification

### Service Health Checks

```bash
# SLM services (installed by install.sh)
systemctl status autobot-slm-backend
systemctl status nginx
systemctl status postgresql

# After wizard provisioning: AutoBot services
systemctl status autobot-backend
systemctl status autobot-frontend
systemctl status autobot-redis
systemctl status autobot-chromadb
```

### API Health Endpoints

```bash
# SLM backend (via nginx HTTPS proxy)
curl -sk https://127.0.0.1/api/health

# AutoBot backend (direct uvicorn — internal only)
curl http://127.0.0.1:8001/health

# AutoBot backend (via nginx TLS)
curl -sk https://127.0.0.3:8443/health

# Redis
redis-cli -h 127.0.0.7 ping       # loopback alias
redis-cli -h 127.0.0.1 ping       # localhost default

# ChromaDB (port 8100, NOT 8000)
curl http://127.0.0.7:8100/api/v1/heartbeat

# Ollama
curl http://127.0.0.1:11434/api/version
```

### Verify Ollama Models

After provisioning, Ollama models may not be installed yet:

```bash
ollama list   # Should show models matching AUTOBOT_*_MODEL vars

# Pull missing models (as autobot user or root)
ollama pull qwen3.5:9b
ollama pull nomic-embed-text:latest
ollama pull llama3.2:1b
ollama pull gemma2:2b
ollama pull phi3:mini
ollama pull mistral:7b-instruct
ollama pull dolphin-llama3:8b
```

**Note:** Ollama models are not pulled automatically during provisioning. They must be pulled
manually or via a post-provision hook.

### Log Locations

| Service | Log Location |
|---------|-------------|
| install.sh | `/var/log/autobot/install-<timestamp>.log` |
| AutoBot backend | `/var/log/autobot/backend.log` |
| AutoBot backend (errors) | `/var/log/autobot/backend-error.log` |
| SLM backend | `journalctl -u autobot-slm-backend` |
| All services | `journalctl -u autobot-* -f` |

**Tip:** If `systemctl status autobot-backend` shows "active (running)" but the API is not
responding, uvicorn supervisor stays alive even when all workers crash. Check with:
```bash
ss -tlnp | grep 8001   # Verify uvicorn is actually bound
```

## Troubleshooting

### Backend Can't Reach Redis

**Symptom:** Backend logs show `ConnectionRefusedError: [Errno 111] Connect call failed ('127.0.0.1', 6379)`.

**Cause A:** `AUTOBOT_REDIS_HOST` not set, defaulting to multi-host IP (e.g., `172.16.168.23`).

```bash
grep AUTOBOT_REDIS_HOST /etc/autobot/backend.env
# If missing or wrong IP:
echo "AUTOBOT_REDIS_HOST=127.0.0.1" >> /etc/autobot/backend.env
systemctl restart autobot-backend
```

**Cause B:** Redis is not running.

```bash
systemctl start autobot-redis
redis-cli ping   # Must return PONG
```

### ChromaDB Port 8000 Conflict

ChromaDB must run on port `8100`. Port `8000` is used by the SLM backend.

```bash
grep AUTOBOT_CHROMADB_PORT /etc/autobot/backend.env
# Must be 8100. Fix if wrong, then restart autobot-backend.
```

### Loopback Aliases Missing After Reboot

Service-to-service calls fail because `127.0.0.3`, `127.0.0.7`, etc. are not configured.

```bash
ip addr show lo | grep "127.0.0"

# Re-add immediately
sudo ip addr add 127.0.0.3/8 dev lo 2>/dev/null
sudo ip addr add 127.0.0.6/8 dev lo 2>/dev/null
sudo ip addr add 127.0.0.7/8 dev lo 2>/dev/null
```

To persist across reboots, add to `/etc/rc.local` (or a systemd `network` override unit).

### SLM Backend Won't Start

```bash
journalctl -u autobot-slm-backend -n 50 --no-pager
# Also check:
cat /etc/autobot/slm-secrets.env   # Must be readable by autobot user
ls -la /etc/autobot/slm-secrets.env  # Must be 640 root:autobot
```

### Ansible Permission Errors During Provisioning

```bash
# Verify autobot user has passwordless sudo
sudo -u autobot sudo whoami   # Must print: root

# Verify Ansible tmp dirs are owned by autobot
ls -la /tmp/ansible_fact_cache /tmp/ansible-retry /tmp/.ansible-cp
# If root-owned, fix:
sudo chown autobot:autobot /tmp/ansible_fact_cache /tmp/ansible-retry /tmp/.ansible-cp
```

### Backend Startup Shows UTC Datetime Warnings

The backend normalizes naive datetimes from Redis to UTC. This warning is harmless if you see:

```
WARNING: naive datetime returned from Redis; normalizing with replace(tzinfo=timezone.utc)
```

### WSL2: 127.0.0.1 Gets ECONNREFUSED Despite Service Listening

WSL2 mirrored networking can cause `127.0.0.1` to be unreachable from within WSL2 in some
configurations. Use `10.255.255.254` as the host IP for service-to-service calls inside WSL2.

## Updating Code

```bash
# Pull latest code to SLM code source
sudo -u autobot git -C /opt/autobot/code_source pull origin Dev_new_gui

# Re-run provisioning (code sync + service restart only)
cd /opt/autobot/autobot-slm-backend/ansible
ansible-playbook \
  -i inventory/localhost.yml \
  playbooks/sync-code-source.yml

# Or restart individual services
systemctl restart autobot-backend
systemctl restart autobot-frontend
```

## Scaling to Distributed Deployment

To migrate the same node to a distributed multi-VM architecture:

1. Update `/etc/autobot/slm-secrets.env` with the real SLM server IP.
2. In the SLM Wizard, add new fleet nodes with their real IPs.
3. Reassign roles from the single host to the appropriate new nodes.
4. Run **Provision** in the Wizard — Ansible reconfigures all backends with the new addresses.

See [`docs/runbooks/DEPLOY_NEW_NODE.md`](../runbooks/DEPLOY_NEW_NODE.md) for per-node setup.

## Service Dependencies

```
SLM Backend (port 8000)
  └── PostgreSQL (port 5432)   [user management DB]
  └── nginx (port 443/80)      [TLS proxy]

AutoBot Backend (port 8001, nginx 8443)
  ├── Redis (port 6379)         [REQUIRED — cache, sessions, task queue]
  ├── ChromaDB (port 8100)      [REQUIRED for KB — vector search]
  ├── Ollama (port 11434)       [REQUIRED for AI — LLM inference]
  ├── PostgreSQL (port 5432)    [only in non-single_user modes]
  ├── Browser Worker (3000)     [optional — web automation]
  └── NPU Worker (8081)         [optional — hardware acceleration]
```

**Startup order:** Redis and ChromaDB must be running before the backend starts. Ollama can be
started after the backend (agents degrade gracefully until models are available).
